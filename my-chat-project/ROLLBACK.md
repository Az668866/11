# 回滚说明

## 回滚触发条件

出现数据保护密钥错误、卡密无法登录/重复发放、权限异常、关键接口持续 5xx、迁移失败、数据库锁等待失控或通话/消息主流程不可用时立即停止放量并回滚。不要在故障期间删除表、批量修数据或反复轮换密钥。

## 最安全的应用回滚

1. 停止新部署流量，保留故障实例日志、Request ID 和数据库指标。
2. 若本次上线后轮换过 `TOKEN_SECRET`，先把它恢复为升级前的值；该值应与固定的 `DATA_PROTECTION_SECRET` 相同。旧后端仍用 `TOKEN_SECRET` 解密持久化数据，使用新令牌密钥直接回滚会导致历史卡密、TOTP 和语音不可读。
3. 回滚到基线后端包，确认 `/health` 和历史卡密登录。
4. 按超级管理员 → 代理 → 租户后台 → 用户模板的相反发布路径恢复基线前端站点完整目录。
5. 清浏览器站点缓存并重新登录。密钥轮换和新会话机制会使旧令牌失效，不应尝试恢复会话。

## 数据库处理

本次数据库修改只新增表、索引和记录，不需要为了应用回滚而删除：

- `auth_sessions`
- `auth_attempt_limits`
- `license_generation_requests`
- `data_protection_state`

旧版本会忽略这些表。保留它们能避免破坏证据，并允许重新部署新版。只有数据库本身出现已确认的数据损坏时，才由数据库负责人在停止写入后从上线前快照恢复；恢复会丢失快照之后的正常业务写入，必须先完成差异评估。

绝对不要删除 `data_protection_state` 来绕过密钥不匹配。若该保护触发，正确动作是恢复原 `DATA_PROTECTION_SECRET`。

## 新旧版本数据兼容

- 新卡密仍写入原 `license_keys` 结构，旧后端可读取，前提是回滚时 `TOKEN_SECRET` 恢复为数据保护密钥对应的旧值。
- 新增数据库会话和幂等记录被旧后端忽略；回滚后所有管理员主动重新登录。
- 新前端依赖新的服务端注销接口。后端回滚时必须同时回滚前端，避免功能表现不一致。
- 外置品牌图片是带哈希静态资源。前端回滚必须上传基线站点完整目录，不能只替换 `index.html`。

## 回滚后验证

依次验证：历史普通/超级卡登录、管理员 MFA、代理列表脱敏、卡密生成与一次兑换、注销后重新登录、用户消息、媒体读取、SSE、语音和视频呼叫。然后核对数据库租户数、卡密状态数、消息数与回滚前记录，确认没有重复发权益或丢失写入。
