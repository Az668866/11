# 租户独占入口部署说明

## Netlify 独立站点模式（本次新增，推荐）

如果希望每个租户看到不同的短域名，例如 `a8k2.netlify.app`，启用
`TENANT_NETLIFY_ENABLED=true`。后端会在租户首次打开后台时自动创建一个
Netlify Site，并把对应的用户端部署到该站点。站点名默认只使用 4 个字符，
避免出现很长的域名；不需要给每个租户配置 Cloudflare DNS 或 Worker。

租户二维码只包含站点域名，租户码和入口令牌写入该站点的
`tenant-entry.json`，页面加载后自动完成绑定。二维码异常时，系统创建一个
新的短域名和站点，旧站点按 `TENANT_ENTRY_LEGACY_DAYS` 保留，旧二维码在
保留期内仍能找到原租户。

Render 需要新增或修改：

```env
TENANT_NETLIFY_ENABLED=true
NETLIFY_AUTH_TOKEN=你的Netlify个人访问令牌
TENANT_NETLIFY_TEAM_SLUG=可选，Netlify团队名称
TENANT_NETLIFY_NAME_LENGTH=4
TENANT_NETLIFY_BUNDLE_ROOT=tenant-site-bundles
TENANT_ENTRY_DOMAIN_SUFFIXES=ykf000.com,netlify.app
```

`NETLIFY_AUTH_TOKEN` 只放 Render Secret。启用 Netlify 模式时不需要
`TENANT_ENTRY_GATEWAY_SECRET`；旧的 Cloudflare Worker 可以停用。现有租户
首次打开租户后台时会自动补建独立站点。

Netlify 官方支持通过 API 创建站点并用 ZIP 部署静态文件；本项目已经把可用
用户端部署包放在后端仓库的 `tenant-site-bundles` 目录中。

下面的 Cloudflare Worker、泛域名 DNS 部分属于旧版 `ykf000.com` 入口模式；
使用 Netlify 独立站点模式时不要部署 Worker，也不要按旧版步骤打开
`TENANT_ENTRY_ENABLED`。旧模式仍保留，用于兼容已经存在的旧入口。

旧版入口功能解决的是“二维码异常时只更换当前租户，而不是重命名所有租户共用的 Netlify 站点”。开启后，系统会按照租户当前可以使用的模板自动创建入口：一个租户的一个模板对应一个独占域名和二维码。模板有多少个，入口就有多少个。入口记录、二维码链接、模板和历史域名都保存在数据库中。

以前已经存在的租户会在后端升级时自动补齐；新租户第一次激活卡密时自动创建。以后平台新增模板，租户下一次打开后台时也会自动增加该模板的入口，不需要手工建域名。

## 需要修改的文件

- Render 后端：`server.mjs`、`render.yaml`、`.env.example`。
- 所有用户端模板：重新部署包含新版 `scripts/user-client.js` 的前端包。
- 租户后台：重新部署包含新版 `scripts/tenant-admin.js` 和 `styles/tenant-admin.css` 的后台包。
- Cloudflare：部署 `cloudflare/tenant-entry-worker/worker.js`，并设置 `wrangler.toml.example` 中的变量。

数据库不需要手工执行 SQL。后端启动时会增量创建 `tenant_endpoints` 和 `tenant_endpoint_domains` 两张表，并为已有租户补齐入口。

## Render 环境变量

先以关闭状态部署一次，确认 `/health/ready` 正常，再完成 Worker 和 DNS 后打开：

```env
TENANT_ENTRY_ENABLED=true
TENANT_ENTRY_DOMAIN_SUFFIXES=ykf000.com
TENANT_ENTRY_GATEWAY_SECRET=至少32位随机字符串
TENANT_ENTRY_LEGACY_DAYS=30
QR_INCIDENT_WINDOW_MINUTES=10
QR_INCIDENT_REVIEW_THRESHOLD=10
```

`TENANT_ENTRY_GATEWAY_SECRET` 只放 Render Secret，并在 Cloudflare Worker 中设置同一个值。不要提交到 Git。`TENANT_ENTRY_DOMAIN_SUFFIXES` 可以填写多个已接入 Cloudflare 的主域名，用逗号分隔；只填写一个域名也可以。

现有的 `PUBLIC_API_BASE=https://api.ykf000.com` 和 `QR_ENTRY_BASE=https://go.ykf000.com` 不要互换。现有 `ALLOWED_ORIGINS`、`REQUIRE_CLIENT_TEMPLATE_ID`、数据库、R2 和 Telegram 变量继续沿用。旧的全局二维码接口仍保留兼容，不会因为开启新功能而失效。

## Cloudflare DNS 与 Worker

在 `ykf000.com` 的 DNS 中添加一条橙色云记录：

```text
类型：A
名称：*
内容：192.0.2.1
代理状态：已代理（橙色云）
```

然后给 Worker 添加路由 `*.ykf000.com/*`。Worker 变量：

```text
BACKEND_API_BASE=https://api.ykf000.com
RESERVED_HOSTS=api.ykf000.com,go.ykf000.com,ykf000.com
RESOLVE_CACHE_SECONDS=30
```

Worker Secret `TENANT_ENTRY_GATEWAY_SECRET` 必须与 Render 完全一致。Cloudflare Universal SSL 需要保持开启，入口才能使用 HTTPS。若控制台已有 `api.ykf000.com` 或 `go.ykf000.com` 的精确路由，请配置为“不运行此 Worker”的更具体路由，避免网关接管 API 和旧二维码入口。

## 上线顺序

1. 备份 Neon 数据库。
2. 部署后端，先保持 `TENANT_ENTRY_ENABLED=false`。
3. 重新部署所有用户端模板和租户后台；前端构建变量仍指向 `https://api.ykf000.com`。
4. 部署 Cloudflare Worker、泛域名 DNS 和 HTTPS。
5. Render 设置上述变量，将 `TENANT_ENTRY_ENABLED` 改成 `true` 并重新部署。
6. 用一个测试租户登录后台，确认“二维码”页为每个可用模板显示一个入口；逐个打开、复制和下载二维码。
7. 点击某一个入口的“二维码异常”，确认只该入口生成新的 4 位子域名；旧域名在 `TENANT_ENTRY_LEGACY_DAYS` 天内仍能找到同一个租户，其他入口不变。
8. 同一租户在 10 分钟内前 10 次点击均立即更换；第 11 次起本次不自动更换，并向 Telegram 管理群发送“更换 / 核实没问题 / 封禁该卡密”三个处理按钮。

## 运行逻辑

用户看到的入口只有 `https://四位字符.ykf000.com/`，租户码和入口令牌由 Worker 写入安全 Cookie，不显示在地址栏。Worker 根据 Host 查询后端，反代该入口绑定的 Netlify 模板；后端在创建会话时再次校验 Host、入口令牌、租户和模板四者是否匹配。轮换只更新当前模板的入口，旧域名进入历史表并按保留天数过期。旧域名仍可到达 Worker 时会自动跳转到最新域名；如果微信在请求到达 Worker 前已经拦截旧域名，旧二维码无法靠服务器自动绕过，必须使用新二维码。不同租户不会共享入口记录，也不会互相触发轮换。

如果只改 Render 的 API 域名而没有部署 Worker、泛 DNS 和新版前端，独占入口不会工作；如果微信提示“非微信官方网页”，那是微信自己的外链确认页，代码不能可靠地绕过，必须让用户点继续访问或使用已备案/可信域名。
